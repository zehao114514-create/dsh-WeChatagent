# 07 · 2026-10-26 的四个修复

这一批不是新功能，是我自己把这套东西跑起来时踩到的四个坑。每个都是「现象 → 根因 → 改法 → 怎么验」四段，方便你对照自己的实例。

---

## ① 搜索永远返回「联网检索不可用」

**现象**：问任何要联网的问题，模型回一句「检索不可用」，或者直接答「我不知道」。

**根因**：`web-search.js` 里的 bing 请求硬编码 `https://www.bing.com/search?...`，并且 `redirect: 'error'`。国内直连 `www.bing.com` 会被跳到 `cn.bing.com`，node 的 fetch 遇到重定向直接抛 `fetch failed`。

**改法**（`0003-bing-cn-fallback.patch`）：

```js
for (const base of ['https://cn.bing.com/search', 'https://www.bing.com/search']) {
  // redirect: 'follow'
}
```

先走 `cn.bing.com`，失败再退 `www.bing.com`；`redirect` 从 `error` 改成 `follow`。

**怎么验**：`node -e "import('./components/qq-bridge/src/core/web-search.js').then(m=>m.bingSearch('DeepSeek Harness 开源')).then(r=>console.log(r.length,r[0]?.title))"`
👉 期望 10 条左右，几百毫秒返回。

## ② 模型自己说「我不会搜」

**现象**：即便搜索通道修好了，模型仍回答「我没有联网能力」。

**根因**：DSH 原生 `web_search` 在插件侧返回的是 `native_unavailable` / `WEB_PROVIDER_UNAVAILABLE` 这类错误，插件没有回退，直接把错误当结果交回给模型。

**改法**（`0004-search-fallback-and-language-filter.patch`）：`model-search.mjs` 在拿到 `native_*` 错误时自动回退到上面那个 bing 通道，结果标 `provider: 'bridge-bing'` 和 `fallbackFrom`，缓存判断也同时认 `dsh-native` 与 `bridge-bing`。顺手加了语种前缀过滤——问中文却返回一堆日文资料时会把它们降权。

**怎么验**：在群里问「今天有什么科技新闻」，回复里应带上具体标题；日志里能看到 `search fallback -> bridge-bing`。

## ③ 机器人一直回旧话题

**现象**：群里刚 @ 它，它却接着四十分钟前的对话往下说。

**根因**：群设成「只回 @」后，没被点名的消息在 `social-engine.js` 里直接 `return`，但那批行仍然是 unread。下次真的被 @ 时，`unread(key, 20)` 把 20 条旧消息一起塞进 prompt。

**改法**（`0005-stale-dispatch-and-song-dedupe.patch`）：派发前加 15 分钟的时间闸，超过的直接跳过；只有当行被标记为 `direct_mention` 或命中唤醒词时才放行。

**怎么验**：日志里的 `dispatch rows=N oldest_age_ms=...`，修后 `oldest_age_ms` 不应超过 `900000`。

## ④ 点歌重复 / 卡死 / 冒出 `[EMO sad]`

三件小事，根因各不相同：

| 现象 | 根因 | 改法 |
|---|---|---|
| 重启后重唱上一首 | 缓冲里的旧点歌被重新拦截一次 | 按 `message_id` 去重（`out\handled-songs.json`）+ 5 分钟时效，超时打 `song_request_stale_ignored` |
| 两首同时唱、卡死 | 锁按「文件 4 分钟没动」判过期，而整首换声要十几分钟 | 锁里存 pid，用 `process.kill(pid, 0)` 判活；撞车打 `SKIP_BUSY` |
| 群里出现 `[EMO sad] 何も…` | 给立绘用的情绪标签被模型一起说出口 | `message-buffer.js` 出口统一 `stripEmoTags`（`0006-strip-emo-tags.patch`） |

**怎么验**：点一首带歌名的歌，日志应依次出现

```
[Social] song_request_intercepted {"song":"梦醒时分", ...}
fetch 梦醒时分
slice out\梦醒时分_0s_45s.wav start=0s len=45s
... Seed-VC ...
verify#1 ok=true ...   VERDICT delivered
```

并且第二次点歌只出现 `SKIP_BUSY 前一个还在跑 pid=...`，不会再起第二个进程。

## 打补丁的顺序

四个补丁互不依赖，按编号打即可：

```powershell
foreach ($p in 3..6) {
  $f = (Get-ChildItem patches\000$p-*.patch).FullName
  git apply --check $f; if ($LASTEXITCODE -eq 0) { git apply $f }
}
```

`reader-api.py` 那条（0001）照旧用 `tools\apply-patch.ps1`，因为安装包里那个文件在工作区外的 `data\workspace\scripts\`。

## 一个提醒

这些补丁只改行为，不改协议。打完记得**重启对应的服务**：搜索/派发属于 bridge，`[EMO]` 剥离属于 bridge 出口，读取服务另算。重启后第一件事是看 `/health` 里的 `pluginRevision` 有没有变——变了才说明新代码真加载了。
